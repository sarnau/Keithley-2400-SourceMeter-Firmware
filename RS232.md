# Keithley 2400 — RS-232 Serial (QSM SCI) Reverse-Engineering Notes

How the firmware drives the rear-panel **RS-232** port. The UART is the **SCI** (Serial
Communications Interface) sub-module of the MC68332's on-chip **QSM** (Queued Serial Module); line
levels are converted by the **ADM202/MAX202** (U4). Addresses are Ghidra addresses = file offsets in
`2400-FIRMWARE.bin` (flat image, MC68332 / CPU32, big-endian). See [DATASHEETS.md](DATASHEETS.md)
(§4 QSM, base `$FFFC00`) for the register/bit reference, [GPIB.md](GPIB.md) for the parallel GPIB
receive path, and [SCPI.md](SCPI.md) for what happens to received bytes afterwards.

This is the RS-232 counterpart of the GPIB receive work in [GPIB.md](GPIB.md) §5/§6: both transports
fill a receive buffer that the **same** SCPI parser drains (see §8 below). The transmit side (§4) is
the counterpart of the GPIB output pump in [GPIB.md](GPIB.md) §6.

---

## 1. Hardware

- **MC68332 QSM / SCI** — asynchronous 8/9-bit NRZ UART, memory-mapped in the QSM register block at
  base **`$FFFC00`**. RXD is a dedicated pin; TXD is shared with PQS7.
- **ADM202 / MAX202** (U4) — RS-232 line driver/receiver; charge-pump ±10 V from +5 V. Converts the
  SCI logic-level UART to/from EIA-232 levels for the rear serial connector. (Purely analog level
  shifting — invisible to firmware.)
- **Interrupt:** SCI → CPU32 via the QSM interrupt, **user vector 64** (`0x40`). The vector table
  entry at `0x4000 + 64*4 = 0x4100` holds `0x3BEBC` → `EXCEPTION_USER_64_RS232`. (The QSPI half of
  the QSM uses vector 65 → `EXCEPTION_USER_65_TRANSMIT_BLOCK` `0x671C`; the QIVR base is programmed
  in `CPU_HW_CONFIG_SPCR`.)

### SCI register map (base `$FFFC00`, as used by the firmware)

| Addr | Reg | Role in this firmware |
|---|---|---|
| `$FFFC00` | QSMCR | QSM config (written once in `CPU_HW_CONFIG_SPCR`) |
| `$FFFC04` | QILR/QIVR | QSM interrupt level + vector base (→ vectors 64/65) |
| `$FFFC08` | **SCCR0** | SCI baud divider `SCBR`: `Baud = SysClk / (32 × SCBR)` |
| `$FFFC0A` | **SCCR1** | SCI control: M (8/9-bit), PE/PT (parity), ILT, TIE, RIE, ILIE, TE, RE |
| `$FFFC0C` | **SCSR**  | SCI status: TDRE (`0x100`), RDRF, IDLE, OR, NF, FE, PF |
| `$FFFC0E` | **SCDR**  | SCI data — read = RDR (received byte), write = TDR (transmit byte) |

Byte accesses read the **low byte** of each 16-bit register (big-endian `._1_1_` in the decompiler):
`SCSR` status bits and the `SCDR` data byte both live in the low half.

## 2. Interrupt path (QSM user vector 64)

```
QSM SCI IRQ  ──►  user vector 64 (0x40)  ──►  table 0x4000 + 64*4 = 0x4100  =  0x3BEBC
```

`EXCEPTION_USER_64_RS232` (`0x3BEBC`) is a **single combined RX+TX service routine** — unlike the
GPIB side there is no swappable handler pointer; the vector points straight at it. On entry it
snapshots status into `RS232_SCSR` (`0x803782`) from `SCSR` and services, in order, the
framing/idle, receive, and transmit conditions below.

### Receive side (RDRF set)
1. Read the data byte from **`SCDR`**.
2. If `gCONFIG_COMM.rs232_8bits_flag == 0` (7-bit mode) mask to `& 0x7F`.
3. **CR → LF** translation: a received `0x0D` is rewritten to `0x0A` (so the parser always sees LF).
4. **`ETX` (0x03) / `CAN` (0x18)** → raise the abort/break flags `RS232_00808546`,
   `gRS232_008012ea`, `gRS232_008012ec = 0x10` (signals the parser to abort the current input).
5. Otherwise, by flow-control mode:
   - **flow control off** → push the byte via `RS232_add_byte_to_receive_buffer` (§3).
   - **flow control on (XON/XOFF)** → intercept `XOFF` (0x13) / `XON` (0x11) from the host to
     pause/resume *our* transmitter (clear/set `RS232_FLAGS_XON`, toggle TIE); any other byte is
     pushed to the receive buffer. When the buffer crosses its high-water mark the routine emits an
     **`XOFF` (0x13)** back to the host and sets `gRS232_SENDING_BLOCKED_FLAG`.

### Framing error / BREAK (FE set)
Reads `SCDR` to clear, raises the same abort flags, sets **`gRS232_FRAMING_ERR_WAIT_IDLE`**
(`0x808722`) and enables the **idle-line interrupt (ILIE)**. Further RX is suppressed until the SCI
line goes **IDLE**, at which point the flag is cleared and ILIE disabled — i.e. after a line error
the firmware resynchronises on the next idle gap rather than feeding garbage to the parser.

### Transmit side (TDRE set, `SCSR & 0x100`)
Streams one byte from `gRS232_OUTPUT_BUF_PTR` / `gRS232_OUTPUT_BUF_COUNT` to `SCDR`, honouring the
XON/XOFF and `gRS232_SENDING_BLOCKED_FLAG` gates. When the output buffer empties it clears TIE
(transmit-interrupt enable) via `RS232_SET_TIE_Transmit_IRQ_enable(false)`. Full detail — the TX
staging buffer, the response pump that fills it, and terminator append — is in §4.

## 3. Receive buffer (`gRS232_receive_buffer`)

The RS-232 receive buffer is a **linear fill buffer**, *not* a masked ring like the GPIB side:

- **`gRS232_receive_buffer`** (`0x8014D4`) — byte buffer, capacity **`0x200` = 512 bytes**.
- **`gRS232_receive_count`** (`0x801328`) — number of bytes filled (the producer / write index).
- **`gRS232_receive_buffer_tail`** (`0x8086E4`) — read index (the consumer position).

`RS232_add_byte_to_receive_buffer` (`0x3C334`, producer, called from the ISR):

- Appends `dataByte` at `gRS232_receive_buffer[gRS232_receive_count++]`.
- **High-water mark `0x180` = 384:** once `count ≥ 384` it returns `1`, which tells the ISR to send
  an `XOFF` to the host (flow control) — leaving ~128 bytes of headroom for bytes already in flight.
- **Hard cap `0x200` = 512:** a byte arriving when `count == 512` is dropped and raises
  `ERR_INDEX_n363` = **error −363 "Input buffer overrun"** via `EventReg_SET_ERROR`.

`RS232_GET_BYTE_FROM_RCVBUF` (`0x3C380`, consumer, `int (byte *buf)`):

- Masks **IRQ level 6** (`CPU_IRQ_SET_MASK_6` / `CPU_ENABLE_IRQS`) around the access so it can't race
  the SCI ISR.
- If `tail < count` → copies `gRS232_receive_buffer[tail++]` into `*buf`, returns **1**.
- When `tail` catches up to `count` (buffer drained) → resets both `count` and `tail` to `0`, and if
  flow control is on and we had sent `XOFF`, emits an **`XON` (0x11)** via `RS232_SEND_BYTES` to let
  the host resume. Returns **0** (no byte available).

So the buffer is refilled from offset 0 each time it fully drains, rather than wrapping. Reset to
empty by `RS232_reset_receive_buffer` (`0x3C42E`).

## 4. Transmit path

Outbound serial is the mirror of the receive side: a SCPI **response pump** fills a single staging
buffer, and the SCI ISR drains it one byte per TDRE interrupt. It is the RS-232 counterpart of the
GPIB BO output state machine (`RESPONSE_OUTPUT_PUMP`, [GPIB.md](GPIB.md) §6).

### TX staging buffer (`gRS232_OUTPUT_BUF`)

Unlike GPIB's queued pump — and unlike even the RX side's accumulate-then-drain buffer — the TX side
holds **one message chunk at a time**:

- **`gRS232_OUTPUT_BUF`** (`0x801FF4`) — the staging buffer the SCI reads from.
- **`gRS232_OUTPUT_BUF_PTR`** (`0x807EAC`) — drain pointer, post-incremented by the ISR.
- **`gRS232_OUTPUT_BUF_COUNT`** (`0x807E98`) — bytes remaining, decremented to 0 by the ISR.
- **`gRS232_SENDING_BLOCKED_FLAG`** (`0x805248`) — "transmit in progress": set when a chunk is
  loaded, cleared when it drains. `RS232_IS_SENDING_BLOCKED` (`0x3C30E`) just reads it.

There is no head/tail ring; a new chunk can only be loaded once the previous one has fully drained
(so senders retry — see the `do { } while` loops below). `RS232_SEND_BYTES` does **no bounds check**,
so the caller is responsible for keeping each chunk within the buffer.

### Low-level loader — `RS232_SEND_BYTES` (`0x3C290`, `int (byte *buf, size_t count)`)

1. If `RS232_IS_SENDING_BLOCKED()` (a chunk is already draining) → return **1** (busy; caller retries).
2. Otherwise copy `count` bytes into `gRS232_OUTPUT_BUF`, set `PTR = buf start`, `COUNT = count`.
3. Under an **IRQ-6 mask**, set `gRS232_SENDING_BLOCKED_FLAG`, clear the `XOFF` state bit, and enable
   **TIE** via `RS232_SET_TIE_Transmit_IRQ_enable(true)` — the first TDRE interrupt then starts the
   byte stream. Returns **0** on success.

`RS232_SET_TIE_Transmit_IRQ_enable` (`0x3C1B0`) simply sets/clears SCCR1 bit **TIE** (`0x80`): the
transmitter interrupt is **event-driven**, enabled only while a chunk is in flight (contrast the
permanently-enabled **TE**, §5).

### ISR drain (TDRE tail of `EXCEPTION_USER_64_RS232`, ~`0x3C120`–`0x3C1AA`)

When `SCSR & 0x100` (TDRE / transmit-register-empty) and a chunk is in flight:

- **host flow control:** if the host has sent `XOFF` (`gRS232_FLAGS & XOFF`) or has not re-sent `XON`,
  the ISR returns without transmitting — TX is paused mid-stream until `XON` arrives.
- **chunk exhausted** (`COUNT == 0`): set the internal `XOFF` state bit, disable TIE, clear
  `gRS232_SENDING_BLOCKED_FLAG` — transmission complete.
- otherwise: write the next byte `SCDR = *gRS232_OUTPUT_BUF_PTR` (TX SCDR write at `0x3C190`),
  `PTR++`, `COUNT--`, keep `gRS232_SENDING_BLOCKED_FLAG` set.

### Response pump — `RESPONSE_RS232_BUILD_RESULTSTR` (`0x3BA74`)

The RS-232 response pump is reached through the **swappable pointer `FUNCPTR_COMM_BUILD_RESULTSTR`**
(`0x8086FC`, the `VOIDFN *` slot in [MEASURE.md](MEASURE.md) §4b). `CHECK_CONFIGURATION_CHECKSUMS`
points it at the per-protocol pump:

| `gCONFIG_COMM.commMode` | pump installed |
|---|---|
| RS-232 | `RESPONSE_RS232_BUILD_RESULTSTR` (`0x3BA74`) |
| SCPI / GPIB | `RESPONSE_SCPI_BUILD_RESULTSTR` |
| IEEE-488.1 | `RESPONSE_488_1_BUILD_RESULTSTR` |

The pump is a small **state machine** on `gRS232_VarPtr->state` (states 0–3; dispatched by a Pascal
compiler switch jump-table at `0x3BAA0` that Ghidra cannot render as a `switch` — the same PC-relative
idiom noted in [MEASURE.md](MEASURE.md) §4b). Each state flushes the accumulated SCPI response via
**`RS232_FLUSH_RESPONSE_BUF`** (`0x3BDE2`) and, at end of message, appends the line terminator via
`RS232_SEND_EOL_MARKER`. If the shared input-abort flag `gRS232_008012ea` is set on entry, it first
calls `COMM_RS232_RECONFIGURE_AND_RESET` (`0x3BA22`).

`RS232_FLUSH_RESPONSE_BUF` (`0x3BDE2`) sends the whole response buffer —
`RS232_SEND_BYTES(gRESPONSE_BUFFER, gRESPONSE_BUFCOUNT)` — optionally appending `0x11` (DC1/XON)
first when its argument is non-zero. *(This function was previously labelled `RS232_SEND_XON`, which
was misleading: it always transmits the full response buffer, not just an XON byte — renamed in the
DB.)*

### Terminator append — `RS232_SEND_EOL_MARKER` (`0x3BDA2`)

The configured output terminator is looked up in **`RS232_LINEEND`** (`0x63892`), a 4-entry table of
string pointers indexed by `gCONFIG_COMM.rs232_terminator` (matching `parse_flash.py`'s
`['<CR>','<CR+LF>','<LF>','<LF+CR>']`):

| idx | field | string |
|---|---|---|
| 0 | `<CR>` | `"\r"` (`0x0D`) |
| 1 | `<CR+LF>` | `"\r\n"` (`0x0D 0x0A`) |
| 2 | `<LF>` | `"\n"` (`0x0A`) |
| 3 | `<LF+CR>` | `"\n\r"` (`0x0A 0x0D`) |

The routine `strlen`s the selected string and transmits it via `RS232_SEND_BYTES` (retrying while the
TX buffer is busy). So, symmetric with the RX side's CR→LF normalisation (§2), the terminator is an
**output-only** concern — appended here after the response body.

Other direct senders built on the same loader: `RS232_SEND_DCL_Device_Clear` (`0x3BA3A`, emits
`"DCL"` + DC1 + terminator on a device-clear) and the XON release in `RS232_GET_BYTE_FROM_RCVBUF`
(§3).

## 5. Configuration — `COMM_RS232_configure` (`0x3C1CC`)

Programs the SCI from the `gCONFIG_COMM` fields (loaded from the EEPROM comm block, §7):

```
SCCR0 = baudRateTable[gCONFIG_COMM.rs232_baudRateIndex];          // baud
SCCR1 = parityTable[rs232_parity][rs232_8bits_flag] | base;       // frame + enables
        base = 0x1008 (ILT|TE)            if commMode != RS232
        base = 0x102C (ILT|RIE|TE|RE)     if commMode == RS232   // RX + RX-interrupt on
```

Then it polls `SCSR`, resets the receive buffer, sets `gRS232_FLAGS = XON`, clears the TX/blocked
state, and re-inits the command/response ring (`RINGERBUFFER_INIT`).

- **Transmitter (TE, `0x08`)** is in *both* base masks, so the SCI transmitter is **always enabled**;
  **TIE (`0x80`) is left off here** and toggled dynamically per message (§4) — config never arms the
  TX interrupt.
- **Receiver (RE, `0x04`) and receiver interrupt (RIE, `0x20`) are only enabled when
  `commMode == RS232`** (the `0x102C` mask). In GPIB mode the SCI is left transmit-only (so a byte
  can still be pushed out, but nothing is received/interrupts on RX).

### Baud table (`WORD_ARRAY_00072E30`, SCBR values; `Baud = SysClk / (32 × SCBR)`)

The baud index comes from the EEPROM (`parse_flash.py`: `['300','600','1200','2400','4800','9600',
'19200','38400','57600']`). The table confirms **SysClk ≈ 16.78 MHz (2²⁴)**: index 0 (300 baud) uses
SCBR `0x6D4` = 1748, and `300 × 32 × 1748 = 16 780 800`.

| idx | spec baud | SCBR | computed @16.78 MHz |
|---|---|---|---|
| 0 | 300 | `0x06D4` (1748) | 300 |
| 1 | 600 | `0x036A` (874) | 600 |
| 2 | 1200 | `0x01B5` (437) | 1200 |
| 3 | 2400 | `0x00DA` (218) | 2405 |
| 4 | 4800 | `0x006D` (109) | 4810 |
| 5 | 9600 | `0x0037` (55) | 9533 |
| 6 | 19200 | `0x001B` (27) | 19418 |
| 7 | 38400 | `0x000E` (14) | 37449 |
| 8 | 57600 | `0x0009` (9) | 58254 |

### Frame table (`USHORT_ARRAY_ARRAY_00072E44`, `[parity][8bit]` → SCCR1 parity/mode bits)

`parity` index: 0 = NONE, 1 = ODD, 2 = EVEN. `8bit` index: 0 = 7 data bits, 1 = 8 data bits.
SCCR1 bits: `M` = `0x0200` (9-bit frame), `PE` = `0x0400` (parity enable), `PT` = `0x0800` (1=odd).

| parity \ bits | 7-bit | 8-bit |
|---|---|---|
| NONE | `0x0000` | `0x0000` |
| ODD  | `0x0C00` (PE\|PT, 7+par) | `0x0E00` (M\|PE\|PT, 8+par) |
| EVEN | `0x0400` (PE, 7+par) | `0x0600` (M\|PE, 8+par) |

(With no parity the frame is 8N1 regardless of the 7/8 selector; `parse_flash.py` only exposes the
parity menu in 7-bit mode. Parity on 8 data bits sets `M` to carry the 9th/parity bit.)

## 6. Flow control

**Software XON/XOFF only** (no hardware RTS/CTS), gated by `gCONFIG_COMM.rs232_flowcontrol_flag`
(EEPROM: `['NONE','XON-XOFF']`). State lives in **`gRS232_FLAGS`** (`0x808470`,
`RS232_FLAGS`): `XON`, `XOFF`, plus internal "`?`/`?<LF>` received" and `0x20` gates used to
hold off auto-XON until a full line has been consumed.

- **Inbound:** host `XOFF` (0x13) → clear our XON, disable TIE (pause our transmitter); host `XON`
  (0x11) → set XON, re-enable TIE if we were blocked.
- **Outbound:** we send **`XOFF` (0x13)** when `RS232_add_byte_to_receive_buffer` reports the 384-byte
  high-water mark, and **`XON` (0x11)** from `RS232_GET_BYTE_FROM_RCVBUF` once the buffer has fully
  drained. `RS232_SET_TIE_Transmit_IRQ_enable` (`0x3C1B0`) toggles the SCCR1 TIE bit to pause/resume
  transmission. `RS232_SEND_BYTES` (`0x3C290`) is the helper used to emit the XON/XOFF bytes.

**Terminator:** the receive ISR normalises **CR → LF**; the EEPROM `RS232_term` field
(`['<CR>','<CR+LF>','<LF>','<LF+CR>']`) selects the *output* terminator appended on transmit.

## 7. Boot-time bring-up and config source

- **Early boot / booter** — `BOOT_SETUP_GPIO_RS232` (`0x145C`) sets `SCCR0 = 27` → **19200 baud**
  (`16.78 MHz / (32 × 27)`) and `SCCR1 = 0x0C` (TE\|RE, 8N1, **no interrupts** — polled). This is the
  rate the booter's S-record uploader uses, matching `firmware_update.py` (19200). The booter's
  polled serial I/O lives in `BOOT_IO_WAIT_FOR_MAGIC` / `BOOT_IO_READ_BUFFER` / `BOOT_IO_SEND_STR`
  (each polls `SCSR` then reads/writes `SCDR`). *(The in-DB comment that previously read "9600" at the
  boot `SCCR0` write assumed a different clock; corrected to 19200.)*
- **Runtime config source** — the operating parameters come from the 8-byte **EEPROM comm block at
  `0x190`** (`24LC16B.bin`, decoded by [parse_flash.py](parse_flash.py)):
  `Mode (GPIB/RS232), SCPI_Adr, baud index, bits (7/8), parity (N/O/E), flow (none/XON-XOFF),
  terminator, GPIB_mode`. These populate `gCONFIG_COMM`, which drives `COMM_RS232_configure`.

## 8. Relationship to the comms stack (convergence with GPIB)

RS-232 and GPIB differ only in **transport**; the drained bytes feed the identical SCPI parser. The
consumer is `COMM_PARSER_STATE_PROCESS_NEXT` (`0x2D242`), which branches on
`gCONFIG_COMM.commMode`:

```
commMode == GPIB  →  gParserInputReceiveStatus = (*gGPIB_GET_BYTE)(&gParserInputCode);     // 16-bit word + flags
commMode == RS232 →  gParserInputReceiveStatus = RS232_GET_BYTE_FROM_RCVBUF(&rs232Char);
                     gParserInputCode = (char)rs232Char;                                    // byte widened
          → TMS9914A_PARSER_SETUP_STATE(gParserInputCode, &gPARSER_STRUCT) → SCPI dispatch
```

`RS232_GET_BYTE_FROM_RCVBUF` is the RS-232 analogue of the GPIB `gGPIB_GET_BYTE` function pointer
(GPIB.md §5): same "fetch next input byte into caller's slot, return availability" contract, so the
parser loop is transport-agnostic.

The **response side converges the same way**: the executor calls the swappable pump pointer
`FUNCPTR_COMM_BUILD_RESULTSTR` (`0x8086FC`), which `CHECK_CONFIGURATION_CHECKSUMS` sets to
`RESPONSE_RS232_BUILD_RESULTSTR` in RS-232 mode or the SCPI/488.1 pump otherwise (§4) — so the SCPI
result builder is transport-agnostic end to end, differing only at the final byte-pusher (GPIB BO
state machine vs RS-232 SCI TDRE drain).

```
                         ┌─ GPIB: TMS9914A IRQ3 ISR (0x35EE6) ─► gGPIB_RECEIVE_BUFFER (2K word ring, &0x7FF)
input bytes ─────────────┤
                         └─ RS-232: QSM SCI ISR (0x3BEBC, vec 64) ─► gRS232_receive_buffer (512-byte linear)
                                              │
                                              ▼
                         COMM_PARSER_STATE_PROCESS_NEXT (0x2D242)   ← gCONFIG_COMM.commMode
                                              │  (drains via gGPIB_GET_BYTE / RS232_GET_BYTE_FROM_RCVBUF)
                                              ▼
                         SCPI parser → dispatch → handler            (see SCPI.md)
                                              │
                                              ▼
                         response ← FUNCPTR_COMM_BUILD_RESULTSTR (0x8086FC, per commMode)
                                              │
                                              ▼
                         TX: GPIB BO state machine (LF+EOI) / RS-232 RESPONSE_RS232_BUILD_RESULTSTR
                             (0x3BA74) → gRS232_OUTPUT_BUF → SCI TDRE drain
```
